# 课文式讲解

把用户的问题讲成一篇**课文**：像一门好课里的一节那样，读者先看到问题，再看到机制，最后知道什么时候用。整篇课文就是这一条回复，图也用文本画在回复里。口吻是讲课的口吻：用“我们”带着看，称呼对方“你”，句子完整，段落之间有过渡。

## 步骤

1. **定对象。** 从参数和上下文确定讲什么、属于下面“讲法骨架”里的哪一类。讲代码时先读代码：定义、主要调用处，有测试就看测试。问题可以从几层来讲时，选最可能的一层，在开头一句点明讲的是哪一层。
   完成标准：能指出核心实现所在的 `文件:行号`，并能用一句话说出它解决什么问题。
2. **选骨架。** 按下表选一行。一个问题跨两类时，以用户最关心的那一类为主，另一类的内容并进对应的小节。
3. **写课文。** 按骨架写，手法见“讲法”。篇幅随问题伸缩：概念和设计写完整一课，通常 4–7 个小标题；一个参数、一个函数的用途写两三段，照样先结论、后例子。
4. **过一遍。** 发出前对照“交稿前核对”逐条检查。

## 讲法骨架

| 问题类型 | 例子 | 讲法 |
| ---- | ---- | ---- |
| 是什么 / 为什么需要 | sampling 是什么、为什么要有门控 | 一句定义（是什么、怎么做、带来什么）→ X 解决的问题（具名场景 + 朴素方案的代价，必要时两个方案对照）→ 工作原理（4–6 步编号）→ 按需选：优势 / 边界 / 实现 / 何时使用 → 一句话讲本质 |
| 怎么工作的 | agent 循环怎么转、一个请求怎么走到后端 | 先和熟悉的东西对比定位 → 编号步骤讲完整条链路 → 文本图复述（每个框对应一步）→ 部件逐个讲，一个部件一段 → 为什么这很重要 |
| 为什么这样设计 | 为什么工具列表顺序固定、为什么 `execute` 从不抛异常 | 问题 → 朴素设计及其代价 → 这个设计（真实代码，小段引用）→ 取舍 → 何时该用、何时不该用 |
| 区别 / 该选哪个 | stdio 还是 HTTP、workflow 还是 agent | 成对小节，各写做法、优势、缺点 → 把选择收成一个判断问题 → 明确建议 |
| 为什么会这样（直觉型） | 为什么模型会编造 ID | “X 更接近 A 而不是 B” → 成对演示（熟悉情况 vs 边缘情况）→ 讲机制，点明优点和缺点出自同一个机制 → 缓解手段写成“把边界推远” |

## 讲法

- **先下结论。** 第一句话说清是什么、怎么做、带来什么，不带标题。
- **具名场景。** 用一个有名字、有数字的具体场景引出问题（“商品 ID `P-999`”“读取 15 个文件”），名字和数字取自真实代码。先摆出朴素方案，说清它“可行，但……”的代价，再引出真正的设计。
- **对上叫法。** 用户的说法和代码、文档里的名字不一样时，第一次出现就并列写出（“来源门控（代码里叫 `provenance`）”），之后只用一个词。
- **编号步骤。** 机制写成 4–6 步编号列表，每一步主语完整（“执行器把结果……”）。
- **冒号引导。** 代码、图、列表前面放一句以冒号结尾的引导句，说明接下来看什么。
- **粗体标签。** 优势、分类写成“**标签：** 一句解释”。
- **取舍句式。** “X 可以消除 Y，但会带来显著的权衡：**没有 A** —— 后果……不过，有一个好处：……”，最后落到“在以下情况下使用 X：”加条件。
- **一个比喻。** 至多一个，用“更接近 A 而不是 B”的句式轻轻带过。
- **预判反问。** 读者会冒出的疑问（“为什么不直接……？”）在它该出现的位置回答。
- **先文后图。** 先用文字讲完，再用图复述；图里每个元素都能在前文找到对应的一句。
- **小标题。** 写成“主题 + 角度”的实词短语（“门控解决的问题”“一次加购怎样完成”）。

## 终端格式

- **代码：** 引用读过的真实代码，单段 30 行以内；代码块前一句说明它在哪（`path/to/file.py:42`）、做什么，省略处写 `# …`。
- **文本图：** 放进 ```text 代码块，第一行用一句中文问句写这张图要回答的问题，只画会变的部分。框线用 Unicode 制表符 `┌ ┐ └ ┘ ─ │`，分叉用 `├ ┤ ┬ ┴ ┼`，箭头用 `▶ ◀ ▲ ▼`。图下说明先看哪里、再看哪里。
- **中英分工：** 英文只留给两类词：代码名（`apply_change`、`StagedChange`），以及英文更短、更贴原意的专有词（agent、tool、backend）。其余说明都写中文，读者是来读中文课文的。图里多一条限制：一个汉字在终端里占两列，写进框里右边的 `│` 就错位，所以框内标签用英文或代码名；框外不受这个限制，行尾注释、箭头旁的说明、图的标题和不带框的列表都写中文。不要为了图面统一把框外说明也写成英文。例如：

  ```text
  草稿要经过哪几道卡？
   ┌──────────┐
   │ gate     │  编号是不是本会话见过的
   └────┬─────┘
        ▼
   ┌──────────┐
   │ apply    │  按当前配置再查一次
   └──────────┘
  ```
- **对照：** 一个变量取不同值时结果怎样，用一张“取值 → 结果”小表。
- **结尾：** 停在一句话讲本质，或“何时使用 / 何时不用”上。

## 交稿前核对

- 第一句话就是结论。
- 每个小标题都是“主题 + 角度”。
- 每段代码都来自这次读过的文件，并标了出处。
- 每个“谁用了它、什么时候触发”的说法，都能指到这次读过的一行代码，触发条件照代码写全。
- 每张文本图的框边和竖线上下对齐，框里只有英文或代码名，框外的说明、注释和列表都是中文，图下面说了怎么读。
- 回复停在本质句或适用场合上；这次讲解没有新建或修改任何文件。
